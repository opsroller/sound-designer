# Build your first sound cue with the sound-designer role

*Tutorial: for someone new to this plugin who wants to see the role produce one finished, documented sound.*

In this tutorial we will ask the sound-designer to make one interface
sound, `ui_button_confirm`, and follow it from brief to a committed,
documented cue. It takes about fifteen minutes. We use a project that
already has a `CLAUDE.md` and a project profile naming its audio tools,
cue contract, provenance log and docs folders.

## Before we start

Install the plugins (once):

```
/plugin marketplace add opsroller/claude-plugins
/plugin install engineering-practices@opsroller
/plugin install sound-designer@opsroller
```

Open Claude Code in the project's repository on a new branch:

```
git switch -c feat/confirm-sound
```

## Step 1: give the brief

Ask the agent:

```
Use the sound-designer agent. Make the cue ui_button_confirm: it confirms
a menu choice; short, soft, positive; plays often.
```

The agent first reports what it learned from onboarding. You should see
it name the audio tools, the cue contract path, the provenance log path,
the loudness target and the docs layout from the profile. Notice that it
does this before touching any file.

## Step 2: read the event list row

Next the agent writes the cue's row (from the `audio-brief-and-spotting`
skill). The output should look like:

```
cue: ui_button_confirm | purpose: confirms a choice | priority: 2
type: one-shot | frequency: often | variations: 3 | spatial: 2D
source plan: synth
```

Notice the variation count: a sound that plays often gets several.

## Step 3: watch the sound being made

The agent follows `sound-effect-creation`: it writes a small generator
(a script or synth patch, in the tool your profile names), renders three
variations named `ui_button_confirm_01` to `_03`, and checks them for
clicks and clipping. You should now see the rendered files and the
generator source in the paths the profile gives.

Play the three files one after another. They should sound like one
family, none louder or longer than the others.

## Step 4: see the shared files updated

The agent adds one line to the cue contract (bus `ui`, a small pitch
and volume random range, a voice limit) and one line per file to the
provenance log reading "generated by" the generator's path. Open both
files and find the new lines.

## Step 5: hear it in context

The agent asks you (or the gameplay-programmer) to call
`ui_button_confirm` from the menu code, then runs the project. Click the
button several times quickly. The sound should play each time without
stacking into noise, and stay below the music's loudest moments.

## Step 6: see the docs updated

Finally the agent updates the project's reference page for the cue
table and reports which docs it touched. The report should name at least
the cue reference page.

## Step 7: commit

The agent commits everything together:

```
feat(audio): add ui_button_confirm sound
```

We now have a cue that is original, traceable, playable by name and
documented. To make many cues at once, see
[How to run a sound pass](../how-to/how-to-run-a-sound-pass.md). To
understand why the role works this way, read
[About the sound-designer role](../explanation/about-the-role.md).
